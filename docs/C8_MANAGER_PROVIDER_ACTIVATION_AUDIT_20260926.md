# C8 Manager / Provider Activation Audit, 2026-09-26

## Question

Can the current plugin be changed from `import_only` to an Extension
Manager-enabled C8 continuing-prefill provider while preserving the pinned
Qwen3.5 BF16/profile correctness contract?

## Answer

Not yet. The standard Manager route is sufficient, but the pinned Host
contract cannot carry or attest the required model/profile identity.

The read-only audit pins:

- Extension Manager
  `vLLM-HUST/extension-manager@cf1ea71e3e2cb81ab06267ef05eddb3e580ea20b`;
- Host candidate
  `vLLM-HUST/vllm-ascend-hust@11382832d9b88e6a7bdf7a20f4d47c7361fd4c8e`;
- the plugin's current inert manifest by SHA256.

Its machine-readable receipt is
[`docs/evidence/C8_MANAGER_PROVIDER_ACTIVATION_AUDIT_20260926.json`](evidence/C8_MANAGER_PROVIDER_ACTIVATION_AUDIT_20260926.json),
generated by `scripts/audit_manager_provider_activation.py`.

## What already works

The Extension Manager can reuse its built-in vLLM Provider:

1. Static manifest `activation.additional_config` values are merged into the
   final vLLM `--additional-config` object.
2. An operator may already supply an existing `--additional-config` JSON
   object on the `vllm-hust-ext run -- vllm serve ...` command.
3. The Manager rejects a launch when static activation and operator values
   disagree on the same key.

This is enough to use the normal route eventually:

- the active manifest fixes
  `c8_continuing_prefill_provider=<plugin module:factory>`;
- the operator supplies deployment-specific profile settings;
- the Host validates and passes those settings to the provider factory.

No project-specific Manager Host Provider and no unofficial `vllm.*` entry
point are needed.

## What does not work yet

### Saved extension configuration is not a generic Host config channel

The Manager keeps arbitrary `extension configure` data under `user_config`,
but its built-in vLLM Provider only projects supported `launch_options` and
static manifest `additional_config` into the command. A calibration profile
placed only in an extension configuration file does not reach AscendConfig.

Until a reviewed generic projection exists, deployment-specific settings must
be supplied in the operator-owned vLLM `--additional-config` object. Model
paths and similar deployment values must not be hard-coded into the published
manifest.

### The Host exposes only a factory path

At PR #35 head, AscendConfig contains only:

```text
c8_continuing_prefill_provider: str | None
```

The factory receives only:

```text
layer_name, num_heads, num_kv_heads, head_size, scale, kv_cache_dtype
```

It does not receive:

- the actual model repository and revision;
- the pinned model-config SHA256;
- the calibration profile SHA256 and provenance;
- the required full-attention layer set;
- a zero-offset attestation;
- TP rank/world information or a profile-loading result.

The provider can reject obvious request-shape mismatches, but it cannot prove
that the tensors belong to the pinned Qwen3.5 profile.

### Offset values cannot be checked in per-request eligibility

PR #35 requires `is_eligible()` to avoid device work and synchronization.
Reading NPU offset tensor values there would violate that contract and may also
break graph capture. The zero-offset requirement must therefore be checked
once while loading the profile or constructing the provider, before request
dispatch and graph capture.

## Minimal Host revision

The next Host candidate should add one Host-owned, JSON-serializable provider
settings object. It should be generic to a C8 continuing-prefill provider, not
named after this project. At minimum it must carry:

- expected model repository, revision and config digest;
- profile path or another Host-owned profile source plus immutable digest;
- calibration provenance and supported hardware;
- required C8 layer IDs and global/TP-local channel expectations;
- explicit zero-offset-only policy for the current symmetric fallback;
- cache-write ownership and expected paged NZ layout.

Host construction must combine those settings with actual runtime facts:

- the model selected by `ModelConfig`;
- TP rank and world size;
- the attention layer name and local head shape;
- the loaded and validated profile result.

Only this immutable construction-time object should reach the provider
factory. Per-request `is_eligible()` remains a shape/state gate, not a profile
loader or device-value validator.

## Candidate activation contract

The active candidate is acceptable only when all of the following are covered
by clean, off-device tests:

1. Disabled manifest or absent provider preserves the built-in Host path.
2. Manager dry-run merges the fixed factory path with operator-owned profile
   settings and rejects conflicting values.
3. Wrong model/revision/config digest, wrong profile digest, incomplete layer
   coverage, nonzero offsets, wrong TP shape or unsupported graph mode fails
   before request execution.
4. The exact ten full-attention layers can construct the reviewed provider;
   the 30 linear-attention layers cannot.
5. Provider decline preserves the native fallback; an exception after
   acceptance propagates fail closed.
6. Wheel/sdist discovery remains side-effect free and disable plus a new
   process restores the built-in path.

The published/default manifest remains `import_only` until these conditions
pass. This audit does not supply calibration values and does not establish
runtime correctness or performance.
