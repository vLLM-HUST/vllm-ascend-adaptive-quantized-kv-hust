# BF16 Target to C8 Provider Reachability Audit, 2026-09-26

## Decision being checked

The owner follow-up fixes the correctness target to `Qwen3.5-35B-A3B` BF16,
TP2, APC, MTP2, async scheduling, and `FULL_AND_PIECEWISE`. It also asks for a
Host/provider version that the extension manager can enable before performance
testing begins.

This audit asks a narrower question: can that BF16 target reach Host Draft PR
#35's C8 continuing-prefill provider merely by enabling the plugin?

## Source result

No. The current source has a reachability gap before provider execution:

1. `AscendModelSlimConfig._add_kvcache_quant_metadata()` enables dense C8 KV
   only when a model quantization description declares `kv_cache_type=C8`.
2. It records C8 layers only when the checkpoint metadata contains
   `k_proj.kv_cache_scale` entries.
3. `AscendC8KVCacheAttentionMethod.create_weights()` changes the layer
   implementation to `AscendC8AttentionBackendImpl` and creates the K/V cache
   scale and offset parameters.
4. Only `AscendC8KVCacheAttentionMethod.process_weights_after_loading()` calls
   `configure_c8_continuing_prefill_provider()`.
5. Draft PR #35 therefore provides a provider boundary inside an already-C8
   checkpoint path. It does not turn an ordinary BF16 model into an INT8-KV
   model and does not define how BF16-target K/V scales and offsets are
   produced, sharded, stored, or validated.
6. The exact public BF16 model revision
   `Qwen/Qwen3.5-35B-A3B@59d61f3ce65a6d9863b86d2e96597125219dc754`
   has no `quant_model_description.json` in its file manifest, so ModelSlim
   auto-detection does not establish C8 reachability.
7. Ascend resets the upstream `calculate_kv_scales` option to `False`; runtime
   scale calculation cannot close this gap on the pinned Host revision.
8. C8 setup initializes missing scales and offsets to `1/0`. Those defaults
   make a source path constructible but are not calibrated metadata and cannot
   be treated as correctness evidence.

The existing exact-model BF16 test uses `Qwen/Qwen3.5-35B-A3B` without an
Ascend quantization description. The exact-model TP2 quantized test instead
uses `Eco-Tech/Qwen3.5-35B-A3B-w8a8-mtp`; it is not the requested BF16 target
and does not cover APC, MTP2, async scheduling, and `FULL_AND_PIECEWISE`
together.

## Scale and offset constraint

The current C8 cache-write formula is `round(x / scale + offset)`, but the
dense fallback reconstructs only `q * scale`. It does not subtract the offset.
Until the native and fallback contracts are made consistent, the BF16-target
profile must use explicit zero offsets and fail closed on any nonzero offset.
This restriction is correctness-critical, not a performance choice.

## Consequence

Changing the plugin manifest from `import_only` to active before closing this
gap would prove only that the manager can import the package. It would not
prove that the required BF16 target dispatches to the provider. Such a build
must not be reported as a usable Adaptive Quantized KV implementation.

The likely intended treatment is BF16 model weights with an INT8 KV cache. If
so, the usable Host/provider version also needs a reviewed policy and data
contract for:

- how K/V quantization scales and offsets are obtained;
- whether they are static per-channel, calibrated, or dynamic;
- how TP2 shards own those parameters;
- where BF16 K/V is quantized before the paged cache write;
- how the paged INT8 layout and metadata survive APC, MTP2, async compaction,
  hybrid attention/Mamba cache bookkeeping, and graph capture/replay;
- how unsupported layers or shapes fail closed without silently changing the
  target.

## Routes and disposition

| Route | What it proves | Disposition |
| --- | --- | --- |
| Use a checkpoint with `kv_cache_type=C8` | PR #35 provider reachability for an already-quantized model | Useful development fixture, but not a substitute for the specified BF16 target |
| BF16 weights plus a reviewed runtime INT8-KV path | The requested target can actually reach paged-INT8 attention | Required product route; Host/provider contract must include quantization metadata and cache-write ownership |
| Activate only the current observer/CPU reference | Extension-manager import and offline reference availability | Insufficient; no runtime provider reachability |

## Minimum BF16 C8 profile contract

The next Host/provider candidate needs a revision-bound profile rather than an
unqualified `--quantization ascend` switch. At minimum it must bind:

- exact BF16 model repository and revision;
- exact Host/provider/plugin revisions;
- every full-attention layer covered by C8 and every hybrid/Mamba layer kept
  outside that treatment;
- per-layer K/V scale shapes before and after TP2 sharding;
- explicit zero offsets under the current symmetric-only fallback contract;
- calibration method, dataset identity, profile digest and supported hardware;
- cache-write quantization ownership and the expected paged NZ layout;
- fail-closed behavior for identity, layer coverage, shape, dtype, offset or
  graph-mode mismatch.

The Extension Manager's built-in vLLM Host provider can eventually carry the
Host `additional_config` used to select this profile and the PR #35 provider.
The project must not register an unofficial `vllm.*` entry-point or a custom
Host provider merely to bypass the missing scale contract. The released
manifest remains `import_only` until an activation test proves that Manager
enablement reaches the pinned provider with this profile.

## Exact target profile shape

The pinned public model config at
`Qwen/Qwen3.5-35B-A3B@59d61f3ce65a6d9863b86d2e96597125219dc754`
has SHA256
`5e4d7f74fec2f360eb9cfbfcd6ec0c4c76e684d3a11caaed259d9fd9bfbc7944`.
Its `text_config` fixes the artifact contract more narrowly than a generic
40-layer model:

- 40 decoder layers alternate three `linear_attention` layers with one
  `full_attention` layer (`full_attention_interval=4`);
- only layers `3, 7, 11, 15, 19, 23, 27, 31, 35, 39` may carry the dense C8 KV
  profile and reach the continuing-prefill provider;
- each full-attention layer has 2 KV heads with explicit `head_dim=256`, so
  each checkpoint scale/offset tensor has 512 global channels;
- under TP2, Host `_prepare_c8_scales()` shards that tensor to one KV head and
  256 channels per rank;
- the complete target profile therefore contains 10 layers times four K/V
  scale/offset tensors, or 40 profile tensors; the 30 linear-attention layers
  must remain outside this treatment.

The profile auditor now understands nested `text_config`, explicit `head_dim`,
hybrid layer types, and TP sharding. It fails closed on a missing
full-attention layer, an unexpected linear-attention layer, a nonzero offset,
or a shape that differs from the global checkpoint contract.
The pinned-config receipt is
[`docs/evidence/QWEN35_35B_A3B_TARGET_CONTRACT_AUDIT_20260926.json`](evidence/QWEN35_35B_A3B_TARGET_CONTRACT_AUDIT_20260926.json),
generated by `scripts/audit_qwen35_target_contract.py`.

## Development-fixture precedent

A read-only audit of the existing local `Qwen3-14B-BF16-C8` development
fixture shows that this profile shape is practical without changing model
weights:

- the model config declares BF16 and the quantization description declares
  `model_quant_type=FLOAT`, `kv_cache_type=C8`;
- all 40 attention layers have K/V scale and offset tensors;
- every tensor has 1024 channels (`8 KV heads * 128 head size`);
- the same global tensors shard to 512 channels per rank under TP2;
- all 80 offset tensors are exactly zero;
- all 80 scale tensors are finite and strictly positive.

The generic standard-library-only validator is
`scripts/audit_c8_profile_artifact.py`; its retained receipt is
[`docs/evidence/QWEN3_14B_BF16_C8_PROFILE_AUDIT_20260926.json`](evidence/QWEN3_14B_BF16_C8_PROFILE_AUDIT_20260926.json).
This proves a reusable metadata format and supports the zero-offset contract.
It does not prove calibration quality, runtime compatibility, or identity with
the Qwen3.5 target. The target still needs its own calibrated profile and exact
provenance.
